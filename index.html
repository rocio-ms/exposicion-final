Repository Structure & Design Principles

mlops-pipeline-project/
├── .github/workflows/ # CI/CD pipelines
├── config/ # YAML Parameters
├── data/ # DVC pointers & artifacts
├── src/ # Modular source code
├── data/ # Ingestion and cleaning
├── models/ # Training and evaluation
└── api/ # FastAPI Endpoints
├── tests/ # Pytest suite (71 tests)
├── dvc.yaml # Pipeline DAG definition
├── Dockerfile # Production image recipe
└── requirements.txt # Dependencies

Strict Decoupling

Clean architectural separation between model training scripts (src/models/) and HTTP serving logic (src/api/). They evolve independently.

Centralized Configuration

Hyperparameters, file paths, and environment settings are exclusively managed via declarative YAML files within the config/ directory, preventing hardcoded values.

CI/CD Automation

Declarative GitHub Actions workflows ready for event-driven executions (e.g., push to main). Automates the entire lifecycle from testing to image publishing.

Considerations Before the First Deployment

IT Operations First-Run Checklist

01

Clone and Install Dependencies

Clone the remote repository and install all required python packages from requirements.txt in an isolated virtual environment.

02

Initialize DVC

Initialize the Data Version Control engine and track the raw dataset using dvc init and dvc add data/raw.

03

Start MLflow Server

Ensure the MLflow tracking server is running (sqlite backend store, local artifact root, port 5001) before triggering any model training execution.

04

Run the Full Pipeline

Execute the pipeline via dvc repro for a fully reproducible first run, then run pytest to confirm all 71 tests pass successfully locally.

05

Configure DockerHub Secrets

Configure DOCKERHUB_USERNAME and DOCKERHUB_TOKEN as GitHub Secrets before the first CI run, or the build job will fail.

06

Configure Dataset Parameters

Decide the dataset scale via params.yaml (max_samples): ~10k rows for fast CI runs vs. the full 120k for the ~91–92% accuracy production model.

Model Registry & Promotion Gate

Safeguarding Production Quality

3 MLflow Runs

Compared on validation accuracy

Accuracy Gate

Must exceed threshold: > 0.87

Production

Promoted in MLflow Model Registry

1 The Gate Mechanism

The best run, determined by validation accuracy during the CI/CD pipeline, is registered in the MLflow Model Registry. It is then immediately evaluated against a hardcoded accuracy gate.

This gate is the main safeguard the IT team relies on. A degraded model that performs worse than the baseline (0.87) can never reach the serving layer automatically.

2 Fallback Strategy

The FastAPI service loads the Production model from MLflow at startup. However, it incorporates a local .pkl fallback if the tracking server is unreachable. This ensures the API stays highly available even during MLflow maintenance windows.

Continuous Training & Monitoring

Handling Data Drift and Model Degradation

Detecting Concept and Data Drift in Production

We utilize Evidently AI to monitor statistical shifts between the original training reference data and live production inference data.

Continuous Monitoring (CM)

  • Tracks Kolmogorov-Smirnov and PSI metrics to detect shifts in feature distributions.
  • Monitors F1-score degradation over time as new ground-truth labels are acquired.
  • Generates HTML reports saved to reports/drift_report.html.

Continuous Training (CT)

  • Automatic retraining trigger: Activated when monitoring metrics exceed the predefined degradation threshold.
  • Pipeline executes a fresh run using dvc repro on updated datasets.
  • Candidate models are registered in MLflow for A/B validation against the current production model.

Ongoing Monitoring & Maintenance Tasks

Routine IT Operations Checklist

  • Feature Drift Monitoring (Evidently AI)

    The system compares 6 text-derived features (length, word count, avg. word length, sentence count, uppercase & digit ratios) against the training reference using PSI. Alerts trigger when PSI exceeds the threshold.

  • Recommended Maintenance Cadence

    Run the monitor.py script on a scheduled cron job (e.g., weekly) and review the generated drift report. Re-run dvc repro manually to retrain if drift is detected or accuracy degrades in production logs.

  • Security & Access Management

    Rotate the DockerHub access token periodically for security compliance. Update the corresponding GitHub Secret (DOCKERHUB_TOKEN) immediately after rotation to prevent CI/CD failures.

  • Dependency Management

    Keep requirements.txt dependencies current to avoid vulnerabilities. Always re-run the full 71-test Pytest suite locally before committing dependency upgrades. Review GitHub Actions run history for failed jobs before merging new code changes.
